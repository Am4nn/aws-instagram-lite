## Setup notes

- `cdk bootstrap` and `cdk deploy` work unchanged with `AWS_ENDPOINT_URL=http://localhost:4566`. No cdklocal needed.
- CloudFormation outputs give real-AWS URLs (`https://<id>.execute-api.us-east-1.amazonaws.com`). Locally call `http://<id>.execute-api.localhost.floci.io:4566` (public DNS resolves it to 127.0.0.1, so it needs internet).
- JWT authorizer + Floci Cognito needs two container env vars: `FLOCI_SECURITY_ALLOW_PRIVATE_JWT_TARGETS=true` and `FLOCI_BASE_URL=http://127.0.0.1:4566`. The flag only trusts literal IPs, and the default issuer is `http://localhost:4566/<pool>`, which it rejects with a silent 401. Issuer on real AWS: `https://cognito-idp.<region>.amazonaws.com/<pool>`.
- The Floci CLI can't pass env vars, so this repo runs Floci from `docker-compose.yml` (`npm run floci:up`).
- `floci reset` wipes resources but keeps CloudFormation stack records, so CDK says "no changes" while nothing exists. `npm run deploy:local` detects this (bootstrap SSM param missing) and deletes stale records first.
- A stack stuck in `DELETE_FAILED` also makes `cdk deploy` report "no changes". The spike tears down before deploying.
- CDK `bucket.addEventNotification()` and `autoDeleteObjects` use Lambda-backed custom resources. Avoided: set `NotificationConfiguration` on the bucket directly, and empty buckets before `cdk destroy`.
- Lambda runs in Docker (`public.ecr.aws/lambda/nodejs:22`). The first invoke pulls the image (slow once), and warm calls take milliseconds.
- CloudWatch alarms are really evaluated (OK → ALARM within about 10 s here, 1-3 min on AWS). SQS metric history outlives `cdk destroy`, so a recreated alarm with the same name can fire right away.
- npm 11 blocks esbuild's postinstall script, and esbuild still works without it.
- (step 2) Browser → Floci Cognito needs `FLOCI_SECURITY_EXTRA_CORS_ALLOWED_ORIGINS` (+ SDK headers in `..._ALLOWED_HEADERS`). Cognito PreSignUp Lambda triggers work.
- (step 3) Inside Lambda, Floci injects `AWS_ENDPOINT_URL=http://localhost.floci.io:4566`; presigned URLs minted there also work from the browser (public DNS → 127.0.0.1). Step Functions retry with jitter + MaxAttempts 0 retriers work.
- (step 5) DynamoDB Streams → Lambda with an `eventName: INSERT` filter works (MODIFY correctly filtered out). Floci runs transactions serially, so real-AWS `TransactionConflict` cancellations can't be reproduced locally; the code handles them anyway.
- (step 6) `AWS::Logs::LogGroup` with a custom name is reported CREATE_COMPLETE but not created, and Lambda `LoggingConfig.LogGroup` is ignored (logs stay in the Lambda container: `docker logs`). Step Functions `ExecutionsFailed` metrics aren't emitted, so that alarm only fires on AWS. SQS DLQ alarms do work end to end.
- (step 7) CloudFront + OAC + private S3 works over HTTP at `http://<id>.cloudfront.localhost.floci.io:4566` (no HTTPS, so the viewer `redirect-to-https` isn't applied). Extensionless S3 keys work. Custom error responses (404 page) aren't applied, and CloudFront Functions don't run. The browser origin must be in `FLOCI_SECURITY_EXTRA_CORS_ALLOWED_ORIGINS` (no wildcards); `deploy:web` handles it.
- (step 7) `FLOCI_STORAGE_MODE=persistent` keeps every resource across container restarts (the default in-memory mode wipes them).
- (step 9) **Lambda Function URL** works (path, query, `Cookie` in; `cookies: [...]` out as `Set-Cookie`). Floci returns the URL as `http://<id>.lambda-url.us-east-1.127.0.0.1:4566/`, which doesn't resolve; call it as `http://<id>.lambda-url.us-east-1.localhost.floci.io:4566`.
- (step 9) **CloudFront → Function URL** works only if the exact host is in `FLOCI_SERVICES_CLOUDFRONT_ALLOWED_PRIVATE_ORIGIN_HOSTS` (no wildcards). `deploy:web` writes it to `.env` as `SSR_ORIGIN_HOST`; docker-compose passes it on, and the container is recreated when it changes. Origin custom headers (`x-origin-verify`) are forwarded.
- (step 9) **Path-pattern behaviours work** (`/_next/static/*` → S3 web, `/media/*` → S3 media, default → Lambda).
- (step 9) **Gap:** when CloudFormation creates or updates a distribution, Floci drops each behaviour's `AllowedMethods`, `CachePolicyId` and `OriginRequestPolicyId`. The default behaviour then only allows GET/HEAD (POST → 403 "Invalid method.") and forwards no cookies or query strings. The CloudFront API keeps them, so `deploy:local` / `deploy:web` copy them from the synthesized template after each deploy (`scripts/src/floci-cdn.ts`). Real AWS needs nothing.
- (step 9) **Gap:** CloudFront Functions still don't run, so the viewer `Host` never reaches the Lambda as `x-forwarded-host` (it sees the Function URL host). The local CloudFront URL is passed to CDK as context (`-c localSiteOrigin=...`, from the previous deploy's outputs) and ends up in the server's `SITE_ORIGINS`, so the CSRF Origin check still works. Redirects are relative, so they work either way.
- (step 9) **Gap:** Floci leaves out zip entries whose path contains `...` when it unpacks Lambda code (a zip-slip guard that also catches Next.js catch-all folders like `[...path]`). Symptom: `Cannot find module .../[...path]/route.js`. Workaround: no catch-all routes; the BFF forwarder is mounted at `[a]`, `[a]/[b]`, `[a]/[b]/[c]`.
- (step 9) Inside a Floci Lambda, `*.localhost.floci.io` resolves to the Floci container (Floci's own DNS), so the server Lambda reaches the HTTP API at `http://<api>.execute-api.localhost.floci.io:4566` and Cognito via the injected `AWS_ENDPOINT_URL`.
- (step 9) OpenNext (`npx open-next build`) works on Windows. It logs an install error for the image-optimization function (a temp path containing `C:`); we don't deploy that function.
